# Game Analysis Reporter

레퍼런스 게임을 분석하여 **클론 개발이 가능한 수준의 구현 명세 보고서**를 `.md` 파일로 생성하는 스킬.
MDA(Mechanics, Dynamics, Aesthetics) 프레임워크는 분석의 렌즈로 사용하며, 보고서의 본질은 "보고 바로 만들 수 있는 기획 스펙"이다.

---

## MDA 프레임워크 — 분석 렌즈로 활용

| 계층 | 관점 | 역할 |
|------|------|------|
| **Aesthetics** | 플레이어 | 목표: 어떤 감정을 줘야 하는가 — 모든 설계 결정의 기준 |
| **Dynamics** | 시스템 | 구조: 규칙이 실행 중 어떤 패턴을 만드는가 |
| **Mechanics** | 개발자 | 수단: 실제로 구현해야 할 규칙·데이터·시스템 |

**분석 방향**: Aesthetics(목표) → Dynamics(구조) → Mechanics(수단) 순으로 역추적
**보고서 비중**: Mechanics 구현 명세가 가장 상세해야 한다. MDA는 "왜 이렇게 만드는가"의 근거를 제공하는 역할.

### Aesthetics 8가지 유형 (LeBlanc et al.)
| 유형 | 설명 |
|------|------|
| Sensation | 감각적 쾌감 — 시청각·햅틱 만족 |
| Fantasy | 다른 세계/존재로의 몰입 |
| Narrative | 드라마, 스토리 긴장감 |
| Challenge | 장애물 극복, 숙련도 성장 |
| Fellowship | 사회적 연결, 협력/경쟁 |
| Discovery | 탐험, 새로운 발견 |
| Expression | 자기표현, 개성 |
| Submission | 루틴, 몰입형 패시브 플레이 |

## 워크플로우

### Step 1: 게임 정보 확인 + 장르 분류

게임명을 확인한다. 제공되지 않았으면 질문한다.
게임명이 확인되면 아래 분류표로 장르를 결정하고, 해당 장르 모듈 파일 경로를 기억한다.

#### 장르 분류표

| 장르 | 식별 키워드 | 모듈 파일 |
|------|-------------|-----------|
| **Match-3 퍼즐** | 매치3, match-3, 블록 터뜨리기, 캔디크러시류, 세 개 맞추기, puzzle match | `genres/puzzle-match3.md` |
| **하이브리드 캐주얼 타이쿤** | 타이쿤, tycoon, 요리게임, 카페, 식당, 레스토랑, 주문 처리, cooking, idle tycoon, Pizza Ready류 | `genres/tycoon.md` |
| **뱀서라이크** | 뱀서라이크, vampire survivors, 탕탕특공대, survivor, auto-shooter, 로그라이트 생존, 자동 공격 생존 | `genres/vampire-survivors.md` |
| **미지원 장르** | 위 세 장르에 해당 없음 | 공통 템플릿만 사용. 섹션 14 비워둠. 보고서 상단에 "(장르 모듈 없음 — 공통 분석만 적용)" 명시 |

### Step 2: 공통 웹 검색 (모든 장르 필수)

아래 카테고리를 **순차적으로** 검색한다. 한국어·영어를 혼용하여 최대한 많은 자료를 수집한다.

#### [소스 우선순위 — 검색 전 숙지]
수집 정보의 신뢰도는 아래 순서를 따른다. Step 2.7 검증 시 활용한다.
```
1순위: 팬덤 위키 / 공식 발표 / 개발사 블로그
2순위: YouTube 플레이 영상 (직접 관찰)
3순위: 앱스토어 설명 / 업데이트 노트
4순위: 전문 리뷰 매체 (TouchArcade, IGN 등)
5순위: 커뮤니티 공략 (Reddit, 나무위키, 디시인사이드)
6순위: 일반 블로그 / 개인 리뷰
```

#### [소스 유형별 수집 목표]

**① 영상 소스 — UI·연출·흐름 직접 관찰**
```
"{게임명}" gameplay walkthrough
"{게임명}" first 10 minutes gameplay
"{게임명}" 플레이 영상
→ 목적: HUD 구성, 연출 타이밍, 팝업 노출 조건, 튜토리얼 흐름 시각 확인
→ 유튜브 썸네일·설명만으로도 아트 스타일 파악 가능
```

**② 위키·공략 — 정확한 수치·규칙 확보**
```
"{게임명}" wiki fandom
"{게임명}" 공략 수치 데이터
"{게임명}" gamepedia
→ 목적: 규칙, 아이템 목록, 수치 등 개발자 수준 데이터 확보
```

**③ 앱스토어 여론 — 페인포인트 역추적**
```
"{게임명}" app store review reddit negative
"{게임명}" 리뷰 단점 불만 환불
→ 목적: 실제 페인포인트 → 수익화 구조 역추적
→ 1~2성 리뷰의 불만 패턴이 수익화 설계를 드러냄
```

#### [Aesthetics 파악 — 플레이어 경험]
```
1. "{게임명}" 게임 리뷰 재미 느낌 매력
2. "{게임명}" game review fun appeal
3. "{게임명}" 중독성 이유 왜 재밌어
4. "{게임명}" addictive why fun analysis
5. "{게임명}" 아트스타일 분위기 감성
6. "{게임명}" art style atmosphere mood
```

#### [Dynamics 파악 — 루프 & 시스템 흐름]
```
7.  "{게임명}" 게임플레이 루프 흐름
8.  "{게임명}" gameplay loop session flow
9.  "{게임명}" 피드백 시스템 보상 구조
10. "{게임명}" feedback reward structure
11. "{게임명}" 난이도 곡선 밸런스 설계
12. "{게임명}" difficulty curve balance design
13. "{게임명}" 리텐션 시스템 복귀 유인
14. "{게임명}" retention daily reward meta
```

#### [Mechanics 파악 — 구현 명세]
```
15. "{게임명}" 규칙 메커니즘 시스템 상세
16. "{게임명}" mechanics rules systems detail
17. "{게임명}" UI 화면 구성 흐름
18. "{게임명}" UI screen layout flow
19. "{게임명}" 재화 종류 획득 소비 경제
20. "{게임명}" currency economy earn spend
21. "{게임명}" 수익화 광고 인앱결제 상품
22. "{게임명}" monetization IAP ads products
23. "{게임명}" 콘텐츠 스테이지 레벨 언락 진행
24. "{게임명}" content stages levels unlock progression
25. "{게임명}" 소셜 길드 랭킹 이벤트
26. "{게임명}" social guild ranking event
```

#### [경쟁·유사 게임 포지셔닝]
```
27. "{게임명}" similar games alternatives
28. "{게임명}" vs {유사게임명} 비교 차이
→ 목적: 보고서 1.3 유사 게임 비교표 및 12.3 차별점 근거 확보
→ 유사 게임명을 모르면 "{게임명} 장르 인기 게임 순위"로 먼저 탐색
```

**공통 검색 최소 횟수: 28회 (소스 유형 3종 + 카테고리 검색 25회)**
정보 부족 섹션은 추가 검색으로 보완. 총 최대 40회.

---

### Step 2.5: 장르 모듈 로드 + 추가 검색

Step 1에서 분류한 장르의 모듈 파일을 읽는다.
`genres/{장르}.md` 파일의 **"추가 검색 쿼리"** 섹션을 확인하고 해당 검색을 실행한다.

- 미지원 장르: 이 단계 건너뜀
- 장르별 추가 검색 횟수: 8~12회

---

### Step 2.7: 수집 정보 검증

모든 검색이 완료된 후 정보의 일관성을 점검한다.

**충돌 해소 규칙**
- 수치 충돌 시: 소스 우선순위(Step 2 상단 참조) 높은 쪽을 채택
- 동순위 충돌 시: 두 값 모두 기재 후 "(출처 상충, 추정)" 표기
- 해소 불가 시: 더 보수적인 수치(낮은 쪽) 채택

**필수 수치 누락 체크리스트**
아래 항목이 비어 있으면 추가 검색을 1~3회 실행한다.
- [ ] 에너지/하트 최대치 및 회복 시간
- [ ] Continue 비용 (첫 번째)
- [ ] 코어 루프 1회 소요 시간 (추정이라도)
- [ ] 재화 종류 및 주요 소비 항목
- [ ] 광고 유형 (Rewarded / Interstitial 여부)

---

### Step 3: MDA 분석 보고서 작성

**반드시 아래 두 파일을 모두 읽은 후 작성을 시작한다.**
1. `report-template.md` — 공통 보고서 구조
2. `genres/{장르}.md` — 장르별 섹션 템플릿 (미지원 장르 제외)

**작성 원칙**
- **Mechanics 섹션이 가장 상세해야 한다** — 수치, 규칙, 엣지 케이스, 화면 상세 포함
- 정보가 없으면 `(추정)`으로 표기하되, 유사 장르 게임 패턴 또는 장르 모듈의 추정 가이드를 참고한다
- MDA 연결은 각 Mechanic 설명 끝에 `→ Dynamic`, `→ Aesthetic` 한 줄로 명시한다
- "정보 없음"만 쓰고 넘어가지 말 것 — 추정이라도 개발자가 참고할 수 있는 내용을 제공한다
- 섹션 14(장르 고유 메커니즘)는 장르 모듈의 템플릿을 그대로 채운다

---

### Step 4: 파일 저장 및 전달

- 파일명: `{게임명}_analysis.md` (영문, 소문자, 띄어쓰기는 `-`로)
- 저장 위치: 프로젝트 루트의 `Docs/` 폴더
  - 경로 확인 순서: 프로젝트 루트 탐지 → `Docs/` 폴더 존재 확인 → 없으면 생성 후 저장
  - 최종 경로 예시: `{프로젝트루트}/Docs/{게임명}_analysis.md`
  - 프로젝트 루트를 특정할 수 없는 경우: `/mnt/user-data/outputs/` 에 저장하고 사용자에게 경로를 안내한다
- 저장 후 `present_files`로 사용자에게 전달

## 품질 기준

보고서가 완성되려면 다음 기준을 **모두** 충족해야 한다.

### 구현 명세 기준 (가장 중요)
- [ ] 핵심 메커니즘마다 규칙, 승리/실패 조건, 수치, 엣지 케이스가 기술됨
- [ ] 주요 화면마다 ASCII 레이아웃 또는 구성 요소 목록이 상세하게 기술됨
- [ ] 게임 상태 전환표 (State Machine)가 작성됨
- [ ] 재화 획득/소비 경로가 항목별로 구체적으로 기술됨
- [ ] 밸런스 수치가 추정이라도 제시됨
- [ ] 피드백/연출이 액션별로 기술됨 (시각/사운드/햅틱)
- [ ] 광고 배치 시점과 IAP 상품 구성이 기술됨
- [ ] 주요 데이터 엔티티와 핵심 필드가 정의됨
- [ ] 섹션 14 장르 고유 섹션이 장르 모듈 템플릿에 따라 작성됨

### MDA 분석 기준
- [ ] Aesthetics 섹션에서 주요 유형이 근거와 함께 선정됨
- [ ] Dynamics 섹션에서 코어 루프·메타 루프·피드백 루프가 명시됨
- [ ] Mechanic마다 `→ Dynamic`, `→ Aesthetic` 연결이 명시됨
- [ ] MDA 연결 분석 표가 작성됨

### 공통 기준
- [ ] 모든 섹션 작성 (정보 없으면 추정값 제시, 추정 불가 시 "직접 플레이 필요" 명시)
- [ ] 수치는 출처 또는 `(추정)` 표기
- [ ] 보고서 헤더에 정보 신뢰도 요약 작성
- [ ] 기술 스택(언어, 엔진) 제외
- [ ] 한국어로 작성

## 주의사항

- 검색 결과 부족 섹션: "정보 부족 — 직접 플레이 후 보완 필요"로 표기하되, 유사 장르 패턴 기반 추정값을 함께 제시
- Mechanics 상세 명세를 MDA 분석보다 우선시한다
- 수익화 모델은 반드시 포함 (앱 성공의 핵심 요소)
- 추정 내용과 확인된 내용을 명확히 구분
- 장르 모듈이 없는 경우에도 공통 템플릿의 섹션 14에 관찰된 핵심 메커니즘을 자유 형식으로 기술한다
