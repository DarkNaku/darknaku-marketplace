# Game Feature 스킬

사용자의 자연어 요청을 받아 게임 PRD Markdown 파일의 기능 목록을 추가·수정·삭제하고, 파일을 깔끔하게 정리하는 스킬.

---

## 1단계: PRD 파일 탐색

파일명에 `prd`가 포함된 Markdown 파일을 우선 탐색한다.

```bash
# 파일명에 'prd' 포함된 .md 파일 (대소문자 무시)
find . -maxdepth 3 -type f -iname "*prd*.md" 2>/dev/null
```

**파일을 찾은 경우**: 해당 파일을 읽고 구조를 파악한다. PRD는 다른 스킬에 의해 다양한 구조로 생성될 수 있으므로, 기능 목록 섹션을 유연하게 인식한다.

기능 목록 섹션의 일반적인 패턴:
- `## 기능 목록`, `## Features`, `## 기능`, `## 요구사항` 등의 헤더
- 그 아래 `- [ ]`, `- `, `* `, `1.` 등으로 나열된 기능 항목

**파일을 찾지 못한 경우**: [3단계: 신규 파일 생성](#3단계-신규-파일-생성)으로 이동.

---

## 2단계: 기존 PRD 수정

### 요청 의도 파악

사용자의 자연어 요청에서 다음을 추출한다:

| 의도 | 예시 표현 |
|------|-----------|
| **추가** | "추가해줘", "넣어줘", "만들어줘", "add" |
| **수정** | "바꿔줘", "수정해줘", "변경해줘", "update" |
| **삭제** | "빼줘", "제거해줘", "삭제해줘", "remove", "없애줘" |

---

### 기능 추가 — 삽입 위치 결정 흐름

기능 추가 요청이 오면 아래 우선순위 순서대로 판단한다.

#### A. 사용자가 명시적으로 순서를 지정한 경우 → 지시에 따름

예시 표현: "로그인 다음에 추가해줘", "3번 뒤에", "맨 앞에 넣어줘"

지시한 항목을 기준으로 바로 뒤 또는 앞에 삽입하고, 다른 판단 없이 진행한다.

#### B. 명시적 지정이 없는 경우 → 의존성 분석

추가할 기능과 기존 기능 목록 간의 **의존 관계**를 분석한다.

의존성 판단 기준:
- **선행 관계**: 새 기능이 동작하려면 기존 기능이 먼저 완성되어야 하는가?
  - 예: "소셜 로그인" 추가 → "로그인 기능"이 이미 목록에 있다면 로그인 직후 삽입
  - 예: "결제 내역 조회" 추가 → "결제 기능"이 선행 필요 → 결제 기능 직후 삽입
- **후행 관계**: 새 기능이 완성되어야 다른 기존 기능이 동작하는가?
  - 예: "사용자 인증 모듈" 추가 → 목록에 "로그인", "회원가입"이 이미 있다면 그 앞에 삽입

**의존성이 명확히 판단되는 경우**: 해당 위치에 자동 삽입하고 이유를 보고에 표시.

**의존성 판단이 불가능한 경우** (연관 기능이 없거나 관계가 불분명):

> 사용자에게 다음을 확인한다:
>
> ```
> 이 기능을 어디에 추가할까요?
>   1. 다음 작업(next task)으로 배정 — 현재 진행 중인 마지막 항목 바로 뒤
>   2. 목록 맨 마지막에 추가
> ```

- **"다음 작업"**: 기능 목록에서 현재 진행 중인 것(예: `- [x]` 완료 항목 다음, 또는 진행 상태 표시가 있는 항목 다음)의 바로 뒤에 삽입
- **"목록 맨 마지막"**: 기능 목록 섹션의 마지막 항목 뒤에 추가

---

### 서브 ID 처리 (순서 보장 ID가 있는 경우)

기능 목록 항목에 순서를 보장하는 ID가 있는 경우 (예: `F-001`, `REQ-03`, `#1` 등), 기존 항목 사이에 삽입할 때 **기존 ID를 변경하지 않고** 서브 ID를 생성한다.

#### 서브 ID 생성 규칙

| 삽입 위치 예시 | 기존 ID 방식 | 생성할 서브 ID |
|--------------|------------|--------------|
| F-001과 F-002 사이 | `F-001`, `F-002` | `F-001a` |
| F-001a 이후 추가 삽입 | `F-001`, `F-001a`, `F-002` | `F-001b` |
| REQ-03과 REQ-04 사이 | `REQ-03`, `REQ-04` | `REQ-03a` |
| 숫자형 `3`과 `4` 사이 | `3`, `4` | `3a` |

서브 ID가 `a`~`z`를 모두 소진하면 `aa`, `ab`... 순으로 확장한다 (실제로 이 상황이 발생하면 사용자에게 ID 재정렬 여부를 묻는다).

#### 예시

```markdown
<!-- 기존 -->
- [ ] F-001 로그인 기능
- [ ] F-002 결제 기능
- [ ] F-003 마이페이지

<!-- "소셜 로그인"을 로그인 직후에 추가 (F-001 선행 의존) -->
- [ ] F-001 로그인 기능
- [ ] F-001a 소셜 로그인 (Google, Apple) — F-001 선행 필요
- [ ] F-002 결제 기능
- [ ] F-003 마이페이지
```

ID가 없는 목록이라면 서브 ID 없이 일반 항목으로 삽입한다.

---

### 기능 수정
1. 기존 항목을 찾아 내용 교체
2. 항목을 찾지 못하면 유사한 항목을 제안하고 사용자에게 확인
3. 수정 전/후를 명확히 보여줌

### 기능 삭제
1. 삭제 전 사용자에게 한 번 확인한다
2. 해당 항목과 관련 하위 항목·설명을 함께 제거
3. 삭제 후 목록 번호/순서 정리 (단, ID 번호는 재정렬하지 않음 — 공백이 생겨도 유지)

### 파일 정리 규칙

수정 후 항상 아래를 확인하고 정리한다:
- 빈 줄이 2개 이상 연속으로 있으면 1개로 줄임
- 기능 목록의 들여쓰기 일관성 유지
- 섹션 헤더 뒤에는 빈 줄 1개
- 파일 끝에 줄바꿈 1개

## 3단계: 신규 파일 생성

PRD 파일이 없을 때, 기능 목록 관리용 파일을 새로 만든다.

**파일명**: `FEATURES.md` (프로젝트 루트에 생성)

```markdown
# 기능 목록

> 이 파일은 프로젝트의 기능 요구사항을 관리합니다.
> PRD가 별도로 생성되면 해당 파일로 내용을 이전하세요.

## 기능 목록

- [ ] [여기에 첫 번째 기능 추가]

---
_마지막 업데이트: YYYY-MM-DD_
```

신규 파일 생성 후, 사용자가 요청한 기능을 즉시 추가한다.

---

## 4단계: 결과 보고

작업 완료 후 반드시 다음을 사용자에게 알린다:

1. **수행한 작업 요약** (추가/수정/삭제한 항목)
2. **수정된 파일 경로**
3. **변경 전후 비교** (해당 항목만 발췌)
4. **삽입 위치 이유** (의존성 기반이면 근거 명시)
5. **현재 전체 기능 수** (선택적으로)

### 보고 예시

```
✅ PRD 업데이트 완료

📄 파일: docs/game-prd.md

변경 내용:
  + F-001a 소셜 로그인 추가
    → F-001(로그인) 선행 의존 관계로 바로 뒤에 삽입
  ~ F-003 결제 기능 수정 ("카드 결제" → "카드/계좌이체/간편결제")
  - F-005 푸시 알림 기능 제거

현재 기능 수: 12개
```

## 주의사항

- PRD에 기능 목록 외 다른 섹션(배경, 기술 스펙 등)이 있으면 **절대 건드리지 않는다**.
- 기능명이 모호하면 ("그 기능 수정해줘") 어떤 기능인지 먼저 확인 후 진행.
- 삭제 시 서브 ID 항목도 함께 삭제 여부를 명시적으로 확인한다.
  - 예: F-001 삭제 요청 시 → "F-001a(소셜 로그인)도 함께 삭제할까요?"
- ID 재정렬은 사용자가 명시적으로 요청하는 경우에만 수행한다.
