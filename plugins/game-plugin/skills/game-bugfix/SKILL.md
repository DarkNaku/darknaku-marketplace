# Game-Bugfix Skill

버그를 **가설 → 검증 → 수정 → 안전 장치** 흐름으로 해결하는 스킬.  
단순히 원인을 추측하는 것이 아니라, 가설을 세우고 실제로 검증한 뒤 수정한다.

---

## 워크플로우

### Step 0: 입력 확인

아무 정보도 없으면 아래를 출력하고 **즉시 종료**한다.

```
⚠️ game-bugfix 스킬을 사용하려면 아래 중 하나 이상을 제공해야 합니다:

   1. 문제 증상 설명
   2. 에러 메시지 / 스택 트레이스
   3. 로그 파일
   4. 스크린샷

예: /game-bugfix {문제 설명 또는 에러 메시지}
```

---

### Step 1: 문제 정의

입력에서 다음 세 가지를 정리한다.

- **기대 동작**: 어떻게 동작해야 하는가
- **실제 동작**: 실제로 무슨 일이 일어나는가
- **재현 조건**: 언제, 어떤 상황에서 발생하는가

정보가 부족하면 추가 질문한다.

```
❓ 문제를 정확히 파악하기 위해 확인이 필요합니다:
   - {필요한 정보}
```

---

### Step 2: 가설 수립

분석한 정보를 바탕으로 가능한 원인 후보를 **가설 목록**으로 정리한다.  
가설은 근거와 함께 제시하며, 가장 가능성이 높은 것을 1순위로 둔다.

```
🧠 원인 가설

   가설 1 (최우선): {가설 내용}
      근거: {이 가설을 세운 이유}

   가설 2: {가설 내용}
      근거: {이 가설을 세운 이유}

   → 가설 1부터 검증합니다.
```

---

### Step 3: 가설 검증

각 가설을 순서대로 검증한다. 검증이 성공하면 해당 가설을 원인으로 확정하고 Step 4로 이동한다.

**검증 방법 (상황에 따라 선택)**

| 상황 | 검증 방법 |
|---|---|
| 코드 로직 문제 | 버그를 재현하는 최소 코드 작성 후 실행 |
| 설정·에셋·씬 문제 | Inspector / 설정값을 직접 확인 또는 변경해 재현 |
| 환경·의존성 문제 | 버전, 경로, 연결 상태 등을 직접 확인 |
| 재현 불가 | 로그·상태 추가 후 조건 좁히기 |

코드로 검증 가능한 경우, 재현 코드를 작성해 실행하고 결과를 확인한다.

```
🔬 가설 {N} 검증 중...

   검증 방법: {검증 방법 설명}
   결과: {성공 / 실패}
   판정: {이 가설이 원인인지 여부}
```

모든 가설이 기각되면 Step 2로 돌아가 새 가설을 추가한다.

---

### Step 4: 원인 확정 및 공유

검증 결과를 바탕으로 원인을 확정하고 사용자에게 알린다.

**자동 검증이 된 경우** (재현 코드 실행, 로그 확인 등으로 가설이 증명됨)  
→ 결과만 보고하고 **바로 Step 5로 진행**한다.

```
✅ 원인 확정

   원인: {확정된 원인 설명}
   근거: {검증 과정에서 확인된 증거}
   유형: {코드 문제 / 비코드 문제}

   → 수정을 시작합니다.
```

**자동 검증이 불가능한 경우** (환경 문제, 비코드 문제 등 직접 확인이 필요한 경우)  
→ 사용자에게 확인을 요청한다.

```
✅ 원인 추정

   원인: {추정된 원인 설명}
   근거: {이 원인으로 보는 이유}
   유형: {코드 문제 / 비코드 문제}

   자동으로 검증하기 어려운 상황입니다. 이 원인으로 수정을 진행해도 될까요? ("예" / "아니요")
```

- **예**: Step 5로 진행
- **아니요**: 사용자의 의견을 듣고 Step 2로 돌아가 가설을 보완

---

### Step 5: 수정

확정된 원인을 바탕으로 문제를 수정한다.

**수정 원칙**
- 증상이 아닌 **근본 원인**을 수정한다
- **수정 범위를 최소화**한다 — 관련 없는 코드는 건드리지 않는다
- 비코드 문제는 수정 방법을 안내하고 사용자가 직접 수행하게 한다

**비코드 수정 안내**
```
⚠️ 수동 수정 필요:
   {수정 위치}: {수정 방법}

완료되면 "완료" 또는 "continue"를 입력해 주세요.
```

---

### Step 6: 수정 검증

수정이 올바르게 됐는지, 그리고 기존 동작을 망가뜨리지 않았는지 확인한다.

**코드 문제인 경우** 아래 두 가지를 순서대로 확인한다.

1. **버그 수정 확인** — Step 3에서 작성한 재현 코드를 다시 실행해 버그가 사라졌는지 확인
2. **기존 테스트 통과 확인** — 프로젝트의 기존 테스트 전체를 실행해 사이드 이펙트가 없는지 확인

```
🔍 수정 검증 중...

   [버그 수정] 재현 코드 실행 결과: {버그 재현 안 됨 / 여전히 재현됨}
   [기존 테스트] 전체 테스트 실행 결과: {모두 통과 / {N}개 실패}

   판정: {수정 성공 / 수정 실패}
```

둘 중 하나라도 실패하면 Step 5로 돌아간다.  
기존 테스트가 실패한 경우, 이번 수정이 원인인지 먼저 확인하고 함께 수정한다.

---

### Step 7: 안전 장치 추가

같은 버그가 다시 발생하지 않도록 안전 장치를 추가한다.  
원인 유형에 따라 방식이 달라진다.

#### 코드 문제 → 회귀 테스트

버그를 재현하는 테스트를 추가해 향후 동일한 버그가 생기면 즉시 감지할 수 있게 한다.

```
// 회귀 방지 테스트
// 이 테스트는 {버그 설명}이 재발하면 실패한다
{언어/프레임워크에 맞는 테스트 형식으로 작성}

  - 버그가 발생하는 조건을 설정하고 (Arrange)
  - 버그를 유발하는 동작을 실행하며 (Act)
  - 올바른 동작을 기대값으로 검증한다 (Assert)
```

테스트가 현재 **통과**하는지 확인한다 (수정이 완료된 상태이므로 통과해야 함).

#### 비코드 문제 → 재발 가능성 판단 후 작업 절차 안내

먼저 재발 가능성을 판단한다.

**재발 가능성이 없는 경우** (일회성 실수, 이미 구조적으로 재발이 불가능한 경우 등)  
→ 안전 장치를 생략한다.

**재발 가능성이 있는 경우** (동일한 작업을 반복할 때 같은 실수가 생길 수 있는 경우)  
→ 올바른 작업 절차를 안내한다. 경고 목록이 아니라, 이 작업을 할 때 어떻게 하면 문제가 생기지 않는지 구체적인 방법으로 설명한다.

```
🛠️ 재발 방지 — 올바른 작업 방법

   {이 버그가 발생하는 작업 상황}을 할 때는 아래 방법을 따르세요.

   1. {구체적인 절차 또는 방법}
   2. {구체적인 절차 또는 방법}
   3. {구체적인 절차 또는 방법}

   이렇게 하면 {어떤 이유로 같은 문제가 생기지 않는지 한 줄 설명}.
```

---

### Step 8: 최종 보고

```
✅ 버그 수정 완료

🔍 원인
   {원인 설명}

🔧 수정 내용
   {수정한 파일 및 변경 내용 요약}

🛡️ 안전 장치
   [코드] {추가된 회귀 테스트 위치 및 테스트명}
   [비코드] {안내한 작업 절차 요약 / 해당 없음}

⚠️ 참고 사항 (있는 경우)
   {추가로 알아야 할 사항}
```

---

### Step 9: 사용자 확인

```
🙋 문제가 해결되었나요? ("예" / "아니요")
```

**예** → 종료  
**아니요** → 이번 수정에서 변경한 모든 내용을 되돌리고 아래를 출력한 뒤 Step 2로 복귀

```
↩️ 수정 내용을 모두 되돌렸습니다. 가설부터 다시 시작합니다.
```

---

## 품질 기준

- [ ] 가설을 검증한 뒤 원인을 확정했는가 (추측으로 수정하지 않았는가)
- [ ] 사용자가 원인에 동의한 뒤 수정을 진행했는가
- [ ] 수정 후 버그가 사라졌는지 검증했는가
- [ ] 안전 장치가 추가되었는가 (코드: 회귀 테스트 / 비코드: 재발 가능성 있을 때만 작업 절차 안내)
- [ ] 사용자가 최종 결과를 확인했는가
