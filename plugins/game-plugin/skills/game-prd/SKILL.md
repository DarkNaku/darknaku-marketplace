# Game PRD Writer

게임에 관한 정보를 인풋으로 받아 PRD(제품 요구사항 명세서) `.md` 파일을 생성하는 스킬.

## 전제 조건

- 인풋: 아래 세 가지 방식 중 하나
  - **분석 보고서 / 기획서 파일**: `.md` 또는 텍스트 파일 업로드
  - **텍스트 직접 입력**: 분석 보고서·기획서 내용을 대화에 붙여넣은 경우
  - **게임 특정 정보**: 게임명, 장르, 플랫폼 등 게임을 식별할 수 있는 정보만 제공한 경우
- 아웃풋: `{게임명}_PRD.md` 파일 — 프로젝트 폴더의 `Docs/` 디렉터리에 저장
- 기술 스택 독립적 (특정 엔진·언어·라이브러리 언급 없음)

## 워크플로우

### Step 1: 인풋 유형 판별

인풋 유형에 따라 아래 분기를 따른다.

---

**A. 완성된 분석 보고서 또는 기획서가 제공된 경우**
- 파일 업로드: `/mnt/user-data/uploads/` 에서 파일을 읽는다.
- 텍스트 붙여넣기: 대화에 포함된 내용을 그대로 사용한다.
- → **Step 2로 이동**

---

**B. 게임을 특정할 수 있는 정보만 제공된 경우** (게임명, 장르 등)
- 분석 스킬(`game-analysis`)을 먼저 실행해 분석 보고서를 생성한다.
- 생성된 분석 보고서를 이후 단계의 인풋으로 사용한다.
- → 분석 완료 후 **Step 2로 이동**

---

**인풋이 전혀 없는 경우**
- "분석 보고서·기획서를 업로드하거나 내용을 붙여넣어 주세요. 게임명만 알고 있다면 그것도 괜찮습니다."라고 안내한다.

---

### Step 2: 분석 보고서 파싱

인풋에서 다음 정보를 추출한다:
- 게임명, 장르, 핵심 재미 요소
- 핵심 메커니즘 및 규칙
- 게임 루프 구조 (코어/메타)
- UI/UX 화면 목록 및 흐름
- 재화/경제 시스템
- 수익화 모델
- MVP 우선순위 및 구현 난이도
- 리텐션 시스템 (데일리 보상, 푸시 알림 조건 등)
- 외부 서비스 의존성 (광고, IAP, 분석 서비스 등)

### Step 3: PRD 작성

`references/prd-template.md`를 반드시 먼저 읽은 후, 추출된 정보를 바탕으로 PRD를 작성한다.

PRD 작성 원칙:

1. **구현 지시형 문체**: "~해야 한다", "~으로 구현한다" 형태로 작성
2. **기술 독립적**: 특정 엔진·언어·프레임워크·라이브러리 언급 금지. 플랫폼(iOS/Android 등) 언급은 허용한다.
3. **완결성**: 분석 보고서에 없는 정보는 장르 표준 관행으로 합리적 추론하여 채움 — 추론한 경우 `(기본값)` 표기
4. **Feature 정의**: 공식 Feature는 스프린트 플랜(섹션 7)의 `- [ ]` 항목이다. 시스템 명세(섹션 3)는 규칙·수치·상세 스펙 전용이며 체크박스를 사용하지 않는다.
5. **체크박스 위치**: `- [ ]` 체크박스는 스프린트 플랜 항목에만 사용한다.
6. **Feature 단위 기준**: Feature는 완성했을 때 그 결과를 사람이 인지할 수 있는 단위여야 한다. 반드시 화면에 보여야 하는 것은 아니며, 단위 테스트로 동작을 확인할 수 있는 로직 단위도 Feature가 될 수 있다. 하나의 기능은 **로직 / 비주얼 / 연출** 레이어로 분리해 각각 별도 Feature로 작성할 수 있으며, 이 경우 스프린트를 달리해 순차 개발하는 것이 권장된다.

   **예시 — 타일 스왑 기능을 레이어별로 분리:**

   | Feature | 인지 방법 | 스프린트 |
   |---------|-----------|---------|
   | `타일 스왑 로직` — 인접 타일 교환 및 매칭 판정 | 단위 테스트 통과로 확인 | Sprint 1 |
   | `타일 스왑 비주얼` — 스왑 애니메이션 및 보드 렌더링 | 화면에서 확인 `depends: [Sprint 1] 타일 스왑 로직` | Sprint 2 |
   | `타일 스왑 연출` — 매칭 성공 이펙트·사운드 | 화면·청각으로 확인 `depends: [Sprint 2] 타일 스왑 비주얼` | Sprint 2~3 |

   **Feature가 될 수 없는 예:**
   - ❌ `스왑 함수 작성` — 함수 하나는 완성해도 사람이 인지할 수 있는 결과가 없음
   - ❌ `매칭 조건 상수 정의` — 다른 코드와 합쳐져야 비로소 의미가 생김

7. **의존성 표기**: 선행 Feature가 있는 항목은 항목 뒤에 `depends: {Feature명}` 형태로 명시한다. 다른 스프린트의 Feature를 참조할 경우 `depends: [Sprint N] {Feature명}` 형태로 스프린트 번호를 함께 명시한다.

8. **외부 서비스 Feature화**: 섹션 6.5에서 정의한 외부 서비스는 반드시 해당 도입 스프린트의 `- [ ]` 항목으로 등장해야 한다.

### Step 4: 파일 저장 및 전달
- 파일명: `{게임명}_PRD.md` (영문 소문자, 공백은 `-`)
- 저장 위치: 프로젝트 루트의 `Docs/` 디렉터리
  - 프로젝트 루트를 확인할 수 없는 경우 `/mnt/user-data/outputs/Docs/` 에 저장하고 사용자에게 경로를 안내한다.
- `present_files`로 사용자에게 전달

## 품질 기준

완성된 PRD는 다음을 충족해야 한다:
- [ ] 특정 엔진·언어·프레임워크에 대한 언급이 없음
- [ ] 시스템 명세(섹션 3)에 체크박스 없음 — 규칙/수치/스펙만 기술됨
- [ ] 스프린트 플랜(섹션 7)의 모든 항목이 `- [ ]` 형식으로 작성됨
- [ ] 스프린트 플랜이 2주 단위로 구성됨 (solo 개발 1~2개월 사이클 기준)
- [ ] 각 Feature가 완성 시 단위 테스트 통과 또는 화면/동작 확인으로 사람이 인지할 수 있는 결과를 만드는 단위임
- [ ] 로직/비주얼/연출이 분리 가능한 경우 별도 Feature로 나뉘어 있음
- [ ] 교차 스프린트 의존성에 `depends: [Sprint N] {Feature명}` 형태로 스프린트가 명시되어 있음
- [ ] 섹션 6.5에 정의된 외부 서비스가 해당 스프린트 `- [ ]` 항목에 등장함
- [ ] 화면 정의가 구현자가 UI를 설계할 수 있는 수준으로 기술됨
- [ ] 수익화 플로우가 코드로 옮길 수 있는 단계별 조건으로 기술됨
- [ ] 리텐션 시스템이 섹션 3에 명시됨
- [ ] 외부 서비스 의존성이 섹션 6.5에 정리됨
- [ ] 결과물이 프로젝트 `Docs/` 디렉터리에 저장됨
