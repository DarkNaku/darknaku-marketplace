# Game-Commit Skill

저장소의 변경 내용을 분석해 개발 목표 단위로 커밋 메시지를 작성하고 커밋한다.

## 전제 조건

- **인풋**: 없음 (호출만으로 동작)
- **아웃풋**: 커밋 완료 보고 (커밋 해시 + 메시지)

---

## 워크플로우

### Step 1: 변경 내용 수집

```bash
git diff --staged --stat   # 스테이징된 변경사항
git diff --stat            # 스테이징되지 않은 변경사항
git status --short         # 추적되지 않는 신규 파일
```

스테이징된 파일이 없으면:
1. `git diff --stat`로 변경된 파일 전체를 사용자에게 보여준다
2. "스테이징된 파일이 없습니다. 전체 변경사항을 커밋할까요?" 확인 후
   - YES → `git add -A` 실행
   - NO  → 사용자가 직접 스테이징할 항목을 지정하도록 안내 후 대기

### Step 2: 개발 목표 파악

```bash
git diff --staged
```

변경 내용을 분석해 **개발 목표**를 유추한다.

**유추 기준**:
- 변경된 파일명, 클래스명, 메서드명, 추가/삭제된 코드의 맥락
- 연관된 변경들이 하나의 목표로 묶이는지 여부
- 목표가 여러 개로 보이는 경우 → 혼재로 판단

**분기 처리**:

#### A. 유추 성공 + 목표 단일
→ Step 3으로 바로 진행

#### B. 유추 실패
목표를 파악하기 어려운 경우 사용자에게 질문한다:
```
변경 내용을 분석했는데 개발 목표를 파악하기 어렵습니다.
이번 작업의 목표가 무엇이었나요?
```
답변을 받은 뒤 → Step 3으로 진행

#### C. 목표 혼재 감지
여러 개발 목표가 섞인 것으로 판단되면:
```
변경 내용에 여러 개발 목표가 섞여 있는 것 같습니다.
[목표 A]: {파일/변경 요약}
[목표 B]: {파일/변경 요약}

분리해서 커밋할까요, 하나로 통합할까요?
1) 분리 커밋
2) 통합 커밋
```
- **분리 선택** → 목표별로 스테이징을 나눠 Step 3을 각각 반복
- **통합 선택** → 대표 목표 하나로 Step 3 진행

### Step 3: 커밋 메시지 작성

파악된 개발 목표를 바탕으로 커밋 메시지를 작성한다.

**형식**:
```
{타입}({범위}): {제목}

{본문 — 선택, 상세 설명이 필요한 경우}
```

**타입 분류 기준**:

| 타입 | 적용 기준 | 스토어 노출 |
|------|-----------|------------|
| `feat` | 새로운 기능/시스템 추가 | ✅ 대부분 |
| `fix` | 버그 수정, 비정상 동작 해결 | ✅ 대부분 |
| `balance` | 수치 조정 (데미지, 쿨타임, 가격 등) | ✅ 경우에 따라 |
| `ui` | UI 레이아웃, 텍스트, 이펙트 변경 | ✅ 대부분 |
| `perf` | 로딩 속도, 프레임, 메모리 최적화 | ✅ 경우에 따라 |
| `refactor` | 코드 구조 변경 (동작 불변, Tidy First) | ❌ |
| `chore` | 위 유형에 해당하지 않는 모든 것 | ❌ |

**제목 규칙**:
- 한국어로 작성
- 50자 이내
- 명령형 동사로 시작 (추가, 수정, 개선, 제거, 변경)
- 마침표 없음

**범위(scope) 규칙**:
- Feature명 사용 (예: `매치3엔진`, `하트시스템`, `킹스컵이벤트`)
- 여러 Feature에 걸치면 가장 대표적인 것 하나
- 공통 시스템이면 `core`, `ui`, `infra` 등 사용

**본문 규칙** (다음 중 하나라도 해당하면 작성):
- 변경 이유가 제목만으로 불명확한 경우
- `balance` 타입에서 수치 변경 내역이 있는 경우
- `fix` 타입에서 재현 조건이 있는 경우

**작성 예시**:

```
feat(하트시스템): 하트 자동 회복 기능 추가

- 최대 5개, 30분당 1개 회복
- 최대치 도달 시 회복 타이머 정지
```

```
fix(파워업): Light Ball이 장애물을 무시하는 버그 수정
```

```
balance(적유닛): 고블린 체력 및 방어력 상향 조정

- 체력: 50 → 80
- 방어력: 0 → 5
```

### Step 4: 커밋 확인 및 실행

작성한 커밋 메시지를 사용자에게 보여주고 확인한다:

```
📝 커밋 메시지:
─────────────────────────────
{작성한 커밋 메시지}
─────────────────────────────
이 내용으로 커밋할까요?
1) 커밋
2) 수정 요청
3) 취소
```

- **커밋 선택** → 커밋 실행
- **수정 요청** → 수정 내용을 받아 메시지를 수정한 뒤 다시 Step 4로 돌아와 재확인
- **취소** → 종료

**분리 커밋의 경우**: 각 목표별로 Step 4를 순차적으로 반복한다.

```bash
git commit -m "{제목}" -m "{본문 (있는 경우)}"
```

커밋 완료 후 결과를 출력한다:
```
✅ 커밋 완료: {커밋 해시 앞 7자리}
   {타입}({범위}): {제목}
```

## 스토어 업데이트 노트 추출 방법

```bash
# 특정 버전 이후 스토어 노출 커밋만 추출
git log v1.0.0..HEAD --oneline \
  | grep -E "^[a-f0-9]+ (feat|fix|balance|ui|perf)\("

# 타입별 분류 추출
git log --oneline | grep "^[a-f0-9]* feat("      # 새 기능
git log --oneline | grep "^[a-f0-9]* fix("       # 버그 수정
git log --oneline | grep "^[a-f0-9]* balance("   # 밸런스
git log --oneline | grep "^[a-f0-9]* ui("        # UI 변경
git log --oneline | grep "^[a-f0-9]* perf("      # 성능 개선
```

`refactor`, `chore` 타입은 위 추출에서 자동으로 제외된다.

---

## 주의사항

- `refactor` 커밋과 `feat`/`fix` 커밋은 분리를 권장한다 (Tidy First 원칙)
- 커밋 메시지는 반드시 사용자 확인 후 실행한다 (자동 커밋 없음)
- 테스트가 실패한 상태에서는 커밋을 권장하지 않으며, 사용자에게 경고한다
